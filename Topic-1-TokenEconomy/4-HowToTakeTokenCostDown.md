# 如何降低 Token 成本 (How to Take Token Cost Down)

> 核心公式：`每百万 Token 成本 = 年化 TCO / 年化总吞吐 Tokens`。商业闭环条件：`成本 < 定价`。2026 年 WAIC 共识：技术指标(FLOPS)已让位财务指标(TCO/每百万Token成本)。

## 1. 成本拆解：Token 为什么贵

### 1.1 TCO 构成
```
TCO = 芯片折旧(3年摊销) + 电费 + 显存/内存 + 网络 + 运维人力
```
推理是持续 OpEx，与训练的一次性 CapEx 不同。行业趋势：CapEx 正从云服务商(CSP)向晶圆代工厂(Foundry)传导。

### 1.2 三大成本驱动因素
1.  **显存带宽瓶颈：** 自回归生成每个 Token 需遍历全部 KV Cache。带宽决定吞吐，而非算力。H100/B200 的价值在于带宽。
2.  **KV Cache 膨胀：** 上下文从 32K -> 256K，KV Cache 可占 80% 显存，并发数暴跌。未做 PagedAttention 时尤为严重。
3.  **SLA 约束：** 首字延迟 TTFT < 300ms，Token 间延迟 TPOT < 50ms。为满足 SLA 必须预留资源，牺牲吞吐换体验。

### 1.3 隐性成本
- 无状态 API 每次重传全量历史：`N 轮对话成本 = O(N²)`
- Agent 心跳/后台任务占 5-10%
- 带 `thinking` 的推理模型：思考链按输出价格计费，是最大隐性账单来源。参考案例：OpenClaw 一晚空转消耗 18.75 美元，60% 来自历史重传。

## 2. 定价模型：看懂账单

| 计费项 | 说明 |
| :--- | :--- |
| 输入 Tokens | 便宜，通常为输出的 1/3 - 1/4 |
| 输出 Tokens | 贵，生成是计算密集型 |
| 缓存命中 | 命中部分按 10% 计费(Anthropic/Google)，未命中按全价 |
| 思考 Tokens | 按输出价计费，需单独监控 |

**结论：** 优化目标 = 减少输出、提高缓存命中率、压缩输入。

## 3. 应用层六大优化策略（立即可做）

### 策略 1: 定期清理/压缩会话 (节省 40-60%)
**问题：** 长对话历史导致输入 Token 指数增长。
**做法：**
- 每 10 轮或 30K Tokens 触发 `Summarize`：用小模型将历史总结为 500 Token 摘要
- 新任务强制开新会话，不复用陈旧上下文
- 禁用不必要的 `auto-compact` 频繁重写

### 策略 2: 智能模型路由 (节省 50-80%)
**问题：** 用 GPT-5/Claude 4 处理简单分类/抽取是浪费。
**做法：**
```
IF 任务 in [分类, 抽取, 简单改写] -> Qwen3-8B / DeepSeek-V3 / 本地 7B
ELIF 需要推理 -> DeepSeek-R1 / Claude 4 Sonnet
ELSE 复杂规划 -> GPT-5 / Claude 4 Opus
```
通过 OpenRouter / LiteLLM 统一网关实现路由和 Fallback。

### 策略 3: 利用 Prompt 缓存 (节省 30-50%)
**前提：** System Prompt 前缀必须字节级一致才能命中。
**做法：**
- 将不变的 System Prompt、Few-shot 示例置于最前
- 将可变的用户输入置于最后
- 监控 `cache_hit_rate`，目标 > 80%
- 对高频 Prompt 预热缓存

### 策略 4: 限制上下文窗口 (节省 20-40%)
**做法：**
- 硬性设置 `max_history_tokens = 32K`，超限截断而非全量发送
- 文件读取时按需切片，而非全量注入 `cat file`
- 对 RAG 场景：TopK 从 20 降至 5，实测精度损失 <2%，Token 降 75%

### 策略 5: 隔离大型操作 (节省 20-30%)
**做法：**
- 探索阶段(搜文件、跑测试)用廉价模型 + 本地工具
- 收敛阶段(最终决策、生成代码)再调用强模型
- 将 `read 100 files` 这类操作改为 `grep + read 3 files`

### 策略 6: 本地模型兜底 (节省 60-80%)
**适用：** 隐私数据、高频低难度任务。
**栈：** `Ollama / vLLM + Qwen3-32B / Llama-3.1-8B`，消费级 4090 即可跑 32B Q4。
**阈值：** 月消耗 > 500M Tokens 时，本地 TCO 开始低于云 API。

## 4. Infra 层优化（自建推理服务）

| 层级 | 优化 | 效果 | 备注 |
| :--- | :--- | :--- | :--- |
| **存储层** | **PagedAttention + Prefix Caching** | 并发 x3-5，Prefill节省50-90% | 显存管理+缓存复用合并，多用户共享System Prompt的KV；vLLM默认开启 |
| **调度层** | **Continuous Batching** | GPU利用率 30% -> 90% | 迭代级调度，替代静态Batching，必开 |
| **计算优化** | **量化 (FP8/INT8)** | 吞吐 x1.5-2，显存减半 | 精度损失 <1%，首选FP8 |
| **计算优化** | **投机采样 (Speculative Decoding)** | 速度 x2-3 | 小模型草稿 + 大模型验证 |

## 5. 监控指标

必须看板的 4 个数：
1.  `输入/输出 Token 比`：正常 3:1，异常则检查是否输出过长
2.  `缓存命中率`：<50% 说明 Prompt 结构需重构
3.  `每任务平均 Token`：按任务类型分组，发现异常任务
4.  `每百万 Token 实际成本`：`(月账单 / 月总 Token)*1M`

## 6. 决策框架：自建 vs 云 API

```
月 Token < 100M  -> 纯云 API + 策略 1-5
100M - 500M      -> 云 API + 本地小模型混合路由
> 500M           -> 评估自建 vLLM 集群，计算盈亏平衡点

盈亏平衡点 = 自建月 TCO / (云 API 每百万定价 - 自建每百万成本)
```

**国产推理卡提示：** 在大语言模型推理上，国产 NPU 已能提供相当商业价值，TCO 优势明显，但需验证 SLA 是否达标。
